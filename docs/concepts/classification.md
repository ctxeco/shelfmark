# Classification

Two rule sets run over a map: the **artifact classifier** decides what kind of
thing each item is, and the **funnel** decides which candidates land in the
proposed default selection. Neither is a model. Neither is a constant table in
a scanner. Both are versioned, SHA-pinned JSON artifacts that the evaluator
loads, checks, and refuses to run without.

## Rules are data, and the data is pinned

`@shelfmark/policy` is zero-dependency and contains no extension list, no
prune segment, no regex and no floor. It contains an evaluator. The rules live
in vendored artifacts beside it:

```
packages/policy/vendor/
  artifact-classes.v1.json          the classifier's rules
  funnel-policy.v1.json             the funnel's rules
  selection-policy.v1.json          referenced for one number (min_bytes)
  classifier-equivalence.v1.jsonl   shared fixture
  funnel-equivalence.v1.jsonl       shared fixture
```

An operator points at their own copy with `ARTIFACT_CLASSES_PATH`,
`FUNNEL_POLICY_PATH` or `SELECTION_POLICY_PATH`; the vendored copies are the
fallback, so a consumer is never rule-blind. A **configured-but-unreadable
path throws** rather than silently falling back — an operator who pointed at a
rule set meant it to be in force.

Each loader emits its provenance line to **stderr** (stdout stays a pure data
channel for walk-comparison tooling):

```
artifact_classes_loaded version=1.0.0-rc2 sha256=… source=… classes=7 extensions=…
funnel_policy_loaded version=… sha256=… source=… rules=7 shapes=8 stub_floor=200
```

Version and SHA are recorded on every map run, and the rule set may not change
under a running map: if a page comes back classified under a different SHA
than the one the run pinned, the workflow fails with
`ArtifactClassesChangedMidRun` — a map classified under two rule sets is void,
and blending them into one report would be worse than failing.

The evaluators are ports of a reference implementation, and shared
hand-authored fixtures assert that the two agree on **(class, rule) pairs** and
**(verdict, shapes) pairs**. Two implementations of one rule set diverging
silently is a failure this design has already been bitten by once.

### The loaders refuse malformed artifacts

Load-time refusals, not runtime surprises:

- An extension claimed by two classes is a contradiction in the artifact —
  it throws, rather than letting whichever class was listed last win.
- A missing escape class throws (`the escape class is missing; refusing to load`).
- A funnel rule with an unrecognized detection kind throws: *"an unrecognised
  rule must fail closed, never be skipped."*
- A funnel regex over 512 characters, or containing a nested quantifier
  (`(a+)+`), is refused at load as a ReDoS risk. The patterns are governed
  data, but the *input* is untrusted customer filenames, so the bound is code
  rather than an argument about provenance. It is conservative on purpose: it
  refuses some innocent patterns, which costs a reviewer one rewording instead
  of costing a customer a worker pinned at 100% CPU by a filename.

## Precedence is the design

```
1. FOLDER PRUNE   any prunable ANCESTOR segment  → machine_generated
2. FOLDER SELF    a folder whose own name is prunable → machine_generated, never walked
3. EXACT NAME     machine_generated_names        → machine_generated
4. EXTENSION      compound tail, then bare tail, then whole-name
5. ESCAPE         unclassified
```

Every decision returns the **rule** as well as the class, in a stated grammar
(`prune_ancestor:<seg>`, `prune_self:<name>`, `is_folder`,
`machine_name:<name>`, `extension:<ext>`, `name:<name>`, `no_rule_matched`).
The standing evidence bar is that a check names itself: a distribution that
cannot say *which* rule produced it is not auditable.

The order is stated in the artifact itself because it is exactly where a
reimplementation silently diverges. **Extension-first would classify half of a
dependency tree as human-authored source** and inflate the corpus by orders of
magnitude — a `.md` inside a dependency directory is that dependency's README,
not the customer's knowledge. Rule 3 beats rule 4 for the same kind of reason:
a lockfile and a config file share an extension and could not be less alike —
one is generated by a resolver and rewritten on every install, the other is a
decision somebody made.

Two details worth knowing before you read a distribution:

- **Attribution goes to the shallowest matching ancestor segment**, and the
  item's own trailing segment is not an ancestor — so a *file* named
  `coverage` does not prune itself.
- **Only one compound tail is probed.** The tail after the *first* dot is
  checked before the bare last-dot tail, so a minified bundle does not read as
  source. That means `vendor.bundle.min.js` probes `bundle.min.js`, misses,
  and lands on the bare tail `js`. This is a **documented limit, preserved as
  written**: if it is ever judged wrong, it is an artifact revision plus a
  fixture re-pin, never a silent fix in the evaluator.

The shipped artifact declares seven classes: `human_prose`, `human_source`,
`machine_generated`, `media`, `opaque_container`, `container`, `unclassified`.

{: .important }
> `unclassified` and `opaque_container` are different statements. `unclassified`
> is the escape: **no rule named this item**. `opaque_container` is a positive
> identification reached through rule 4 — we know what it is, and its bytes are
> opaque by construction. Collapsing the two is how a real gap in the
> vocabulary hides. In the corpus this was built against, the escape hatch was
> holding 21.4% of bytes across 37 unknown extension buckets — a whole missing
> class, found only because escape-hatch volume was *measured* rather than
> ignored.

## Pruning happens at the folder boundary

`shouldWalk` is derived from `classify()`, not implemented separately:

```ts
shouldWalk(folderName: string, path = ''): boolean {
  return this.classify(folderName, true, path).classId !== MACHINE_GENERATED;
}
```

When it answers false, the walk **never descends**. It records instead:

- `foldersPruned` increments;
- the folder's Graph `size` — a **recursive** subtree size — is added to
  `reconciliation.prunedFolderBytes`;
- an entry `{ path, rule, size }` goes into the prune manifest, so the ledger
  can say which rule pruned which subtree and how many bytes were left
  unopened;
- a narration line names it.

This is where the economy lives. On the reference drive, refusing to descend
into dependency directories turned a 327,140-item walk into 15,657 items. The
pruned bytes are still accounted for — they are simply accounted for **without
being walked**, which is the entire trick.

Consent exclusions prune at the same boundary, under the rule id
`consent_excluded`. See [the consent model](consent-model.md).

{: .note }
> A prune-list change is a **re-walk**; an extension-table change is not.
> Pruning happens during enumeration, so adding a prune segment would
> reclassify already-walked items as machine-generated while leaving them out
> of the pruned-subtree byte bucket — and the reconciliation would silently
> stop reconciling. The artifact says this out loud, and its own revision
> notes record a change that was therefore refused.

## The funnel: subtraction in a pinned order

The funnel takes the classifier's output and proposes a default selection.
Candidates are files of the artifact's declared candidate class
(`human_prose`, files only). Everything else gets the verdict
`not_candidate:<class>` — a stated non-answer, not an absence.

Classes are **recomputed, never trusted**. Walk records may carry
`artifact_class` fields recorded at walk time by whatever version ran then;
the evaluator re-classifies every record under the version the policy pins,
and **refuses to evaluate** if the loaded classifier's version differs from
the pin. An evaluator that trusts the recording measures a funnel over a
population that no longer exists.

Subtraction rules are applied **in array order, and the array order IS the
precedence**. The loader proves it rather than assuming it: the artifact's
declared `precedence` list must equal the rule order with `propagation`
inserted and the collapse rule last, or it throws. `fingerprint_collapse` must
be the final rule, because it judges the survivors of every other rule. First
match wins; each rule reports the files and bytes it took, including rules
that took nothing.

The shipped precedence:

```
archived_dump_copy        (location scope)
stub_under_200b           (document scope; floor referenced, not duplicated)
receipt_shape             (document scope)
machine_output_in_prose   (document scope)
third_party_publication   (document scope)
propagation
duplicate_fingerprint     (corpus scope, last)
```

`stub_under_200b` carries no literal floor. It references
`selection-policy.v1.json#/parameters/min_bytes`, and a rule that carries a
literal floor *beside* the reference is a load-time error — the number has
exactly one home.

**Propagation is asymmetric, and the loader enforces the asymmetry.** A
document-scoped subtraction extends to every fingerprint-identical copy still
standing; a location-scoped subtraction never propagates. The artifact states
why in one line: the archived copy's exclusion says where the copy sits, not
what the document is, and propagating it would remove the surviving original.

Finally, the evaluator refuses to emit a funnel that does not add up:

```
candidates − Σ(named subtractions) === default_selection,  in files AND bytes
```

If that fails, it throws. A funnel that cannot add does not ship. See
[honest accounting](honest-accounting.md).

## Sensitive shapes: report, never subtract

When the funnel recognizes a sensitive-looking file — credential shapes, tax
documents, identity scans, bank statements, payroll, legal, insurance,
pastoral — it **reports** it and subtracts nothing. The rationale in the
artifact is blunt: *a system you cannot put your tax returns into is a worse
drive search.* Live-credential shapes get rotate-don't-exclude advice beside
the selection, because a live key in a corpus is a key-hygiene problem, not a
privacy one.

This is enforced **structurally at load**, not by convention:

```ts
export const FORBIDDEN_FRAGMENTS = [
  'never_suggest', 'neversuggest',
  'ask_first',     'askfirst',
  'hold_back',     'holdback',
] as const;
```

Those fragments may not appear as an object key **or** as a rule id anywhere
in the policy — both halves are checked, because the rule-id half was a real
hole a test battery caught mid-build. On top of that, `sensitive_shape_rules`
must carry `subtract: "NEVER"` literally, every shape must carry
`report: true` and `subtract: "NEVER"`, and a shape id may not also appear
among the subtraction rules. Any of these fails the load with a
`FunnelPolicyError` naming the violation.

The one restraint that *did* survive from an earlier, retired design is a
**rendering** rule, not a gate: sensitive shapes are shown as **counts** —
over candidates and over the default selection, zeros included — never as a
browsable ranked list of paths. A ranked table of those paths on one screen
*is* the dossier. Per-shape counts do not sum, because one document can match
several shapes.

## Ranking produces an ordering, never a verdict

The selection policy's own text is unusually direct about what a rank is not:
not an importance claim, not a threshold, not a quality judgement. *"A low rank
means 'cheap evidence did not distinguish this', never 'this document is
bad'."* The cut is a budget decision made by a human or a spend limit.

In this port, the ledger goes further: **it emits no rank at all.** The
suggestions document records

```json
"ranking": {
  "ranked": false,
  "reason": "no portable ordering spec published for the funnel port; selection-policy weights are unvalidated (its weights_note) — rank omitted, not invented"
}
```

and the rows are written in path codepoint order — which is not a quality
ranking and is not presented as one. The UI says so on screen rather than
letting path order read as merit order.

{: .warning }
> **The weights are unvalidated.** The selection policy's own `weights_note`
> says so: they were chosen to make two signals jointly dominant because that
> pairing is the argument, and they are not fitted to any measured outcome.
> On the original validation corpus, **randomized weights reproduced 77% of
> the top-100 selection against the declared weights' 81%** — whatever signal
> the coefficients carry is nearly indistinguishable from noise. Treat any
> ordering as a convenience, not a judgment. See
> [known limitations](../project/known-limitations.md), and note that PRs
> tuning weights are declined without a validation corpus.

Determinism is still taken seriously even where the ordering carries no claim.
Every ordering comparison goes through a codepoint comparator rather than
JavaScript's default UTF-16 code-unit compare, so the port matches the
reference implementation on astral-plane characters; the fingerprint collapse
keeps the shallowest path, tie-broken on raw path codepoints and then id —
arbitrary, but **stated**, so the same corpus keeps the same copy every run.
