# Internationalization

`@shelfmark/ui` ships two locales, `en` and `es-MX`, as three files that must
stay in lockstep: `i18n/types.ts` (the closed key union), `i18n/en.ts`,
`i18n/es-MX.ts`.

## The parity gate

`packages/ui/scripts/check-parity.mjs` fails the build on any key present in
one locale and missing in the other. It runs as the **first** step of the ui
package build, so a missing translation cannot ship. `t()` falls back
`es-MX → en → the key string itself` at runtime, but the gate exists so the
fallback is a safety net, not a lifestyle.

## The known blind spot

A user-visible string built by **concatenating** translated fragments escapes
the gate — each fragment passes parity while the assembled sentence is
ungrammatical in one locale. The components defend against this by returning
string *arrays* where a separator is needed (the separator is markup, not
translated text) and by building outcome lines from complete keys. Keep doing
that; do not concatenate translated fragments.

## Numbers and dates

Numbers format through `Intl.NumberFormat(locale)` — the extraction fixed a
hard-coded `en-US` that rendered wrong thousands separators for es-MX. Dates
already used the active locale. Byte-size unit labels (B/KB/MB/GB) are
deliberately untranslated.

## Adding a locale

Add the file, extend the locale type, extend the parity script's locale list,
and translate all keys — the gate will hold you to completeness. Closed
vocabularies (skip reasons, funnel rules, artifact classes) render unknown ids
verbatim as data, so a missing label never crashes a screen.
